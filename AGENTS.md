# AGENTS.md — правила ИИ-разработчика

Репозиторий: `luxad1198/home`. Это веб-приложение для создания КП на поставку оборудования (ООО «РТСтандарт», ИП Захаров, ИП Глазырин). Цель — **законченные проверенные изменения**, без лишнего анализа и нарушения существующих функций.

## 1. Устройство проекта

- `index.html` — интерфейс и разметка документов; `style.css` — предпросмотр A4 и стили печати; `app.js` — логика, расчёты, импорт/экспорт и сохранение состояния.
- Используются HTML/CSS/JavaScript, `docx.js` (экспорт DOCX), JSZip/XML (импорт DOCX), `window.print()` (печать/PDF), `localStorage` (данные формы).
- Ориентируйся на **актуальный код**, а не только на историю чата. Не предполагай наличие сборки, фреймворков или автотестов без проверки. Не вводи крупные зависимости и новую архитектуру без необходимости и согласования.
- Ознакомься с этим файлом в начале работы с репозиторием; не перечитывай и не пересказывай без причины в рамках той же задачи, если он не изменился.

## 2. Тип поручения и приоритеты

**Приоритеты решений:** корректность результата и сохранность данных → отсутствие регрессий → минимальные необходимые изменения → экономия времени и квоты.

- **Аудит:** исследуй и сообщи результаты, **не меняя код**, если исправления не запрошены.
- **Исправление:** определи ожидаемое поведение, по возможности воспроизведи ошибку, найди причину, **исправь и проверь**; не заканчивай только отчётом, когда реализация возможна.
- **Новая функция:** реализуй минимальный законченный вариант и проверь основные/пограничные сценарии.
- **Несколько ошибок:** самостоятельно выбери порядок, исправляй последовательно и проверяй каждый законченный этап. Критичность: (1) потеря данных, неверные финансовые итоги и отказ ключевых функций; (2) сбой импорта/экспорта/сохранения; (3) дефекты оформления и интерфейса; (4) косметика. Учитывай зависимости и область влияния.

Не требуй промежуточного одобрения очевидных исправлений. Если весь объём недостижим, сначала закончи и сохрани важнейший проверяемый этап, затем перечисли оставшееся. Не выдавай частичную проверку за полный аудит.

## 3. Диагностика, вопросы и экономия Work

Изучи относящиеся к проблеме файлы, проверь обоснованную гипотезу и **переходи к реализации, как только причины достаточно ясны**. Расширяй поиск только по необходимости. Не перечитывай неизменённые файлы, не повторяй тесты при тех же условиях и не проводи полный аудит для локальной задачи. При повторяющемся сбое инструмента зафиксируй ограничение, попробуй разумную альтернативу, не утверждай о непроверенном результате.

Самостоятельно выбирай локальные обратимые технические решения. Спрашивай только тогда, когда неясно ожидаемое поведение, есть существенно разные подходы, меняется важная бизнес-логика/архитектура или возможны необратимые последствия. При необходимости предложи до трёх вариантов с краткой рекомендацией. Не повторяй вопросы, на которые уже ответили.

Экономия квоты не должна ухудшать корректность, безопасность или необходимые проверки. Не обещай автоматическую фоновую работу после завершения сеанса.

## 4. Сохранность функций и документов

Сохраняй работоспособность трёх форм КП, таблицы оборудования, калькулятора и налоговых расчётов, импорта DOCX (добавление/замена/отмена), условий поставки, экспорта Word, печати/PDF и восстановления состояния через `localStorage`. Не меняй ставки, реквизиты, формулы и юридические формулировки без прямого задания. Общие изменения проверяй для всех затронутых компаний.

**Веб-предпросмотр, Word и PDF** должны быть согласованы по содержанию, структуре и визуальному восприятию; пиксельное совпадение не требуется из-за различий движков. При изменениях в документах проверяй применимые параметры: A4 и поля, шрифты, ширины таблиц, длинные строки, переносы и разрывы страниц, условия, суммы, подписи, многостраничные КП. Не улучшай один формат ценой ухудшения других и не заявляй о визуальной проверке, если её не выполнял.

## 5. Проверки

Объём тестирования соразмерен риску:
- Локальный баг — исходный и исправленный сценарии плюс непосредственно связанные функции.
- Расчёты — типовые и граничные значения, налоги затронутых компаний.
- Импорт DOCX — адресные тесты по `scripts/IMPORT_TESTS.md` (добавление/замена, отмена, повреждённые файлы, откат); проверку `roundtrip` с реальным экспортом Word запускай, только когда затронута совместимость форматов.
- Вёрстка/экспорт — предпросмотр и затронутые DOCX/PDF, длинные и многостраничные документы.
- **Полный технический аудит проекта** — только по прямому запросу. Полный набор из 12 smoke-тестов — лишь один уровень проверки, допустимый при общих/рискованных изменениях; это не полный аудит.

При наличии Node.js после правок JS запускай `node --check app.js`; для ключевых функций используй базовые тесты `scripts/smoke-tests.cjs` по матрице `scripts/BASELINE_TESTS.md`, выбирая нужные проверки по риску; не запускай полный набор без необходимости. Экспортные тесты выбирай **по затронутому формату и компании** (команды: `scripts/EXPORT_TESTS.md`): Word — настоящий DOCX и проверка OOXML, при необходимости визуализация через LibreOffice; PDF — печатный Chromium. Если затронуты оба формата, проверь оба. PDF проверяй **только по необходимости**, если изменение влияет на печатное КП. **Основной способ — Playwright в доступной локальной/рабочей среде:** `scripts/generate-print-pdfs.cjs`, затем `scripts/check-print-pdfs.py`; проверяй созданные PDF; **DOCX/PDF и архивы передавай владельцу только по запросу**. При визуальных изменениях предоставляй скриншоты затронутого интерфейса или печатных документов; если получить изображения технически невозможно, явно укажи ограничение. **GitHub Actions `Verify print PDF` — резервный способ** при недоступности локального Playwright/Chromium или блокировке генерации: ручной запуск на ветке PR. Не трать время на повторные попытки через недоступный диалог печати Work. Если нет инструмента для запуска Actions, дай владельцу название ветки и инструкцию `scripts/PRINT_PDF_TESTING.md`. Не заявляй об успешной проверке без полученного результата: для адресного smoke-теста убедись, что **фактически выполнен хотя бы один нужный сценарий** (проверь имена и число `pass`, а не только код 0); экспорт проверяй по **свежесозданному файлу текущей ветки**. Не запускай повторно без причины. Для рискованных операций применяй изолированные тестовые данные. **Никогда не заявляй о тестах, которые не выполнял.**

## 6. GitHub — обязательные ветки, PR и разрешение владельца

**Запрещено изменять `main` напрямую, включая правки `AGENTS.md`.**

Для изменений: (1) проверь актуальную `main`, создай отдельную ветку `fix/...`, `feature/...` или `docs/...`; (2) измени и проверь код в этой ветке, сохрани осмысленные коммиты; (3) создай Pull Request **в `main`**, приложи краткое описание и фактические проверки; (4) **остановись до объединения и дождись явного разрешения владельца в чате именно на этот PR**.

Одобрение одного PR не распространяется на другие. Молчание, успешные тесты или создание PR не дают разрешения. Если после одобрения появились существенные изменения — получи новое подтверждение. При замечаниях дорабатывай ту же ветку и PR.

Без явного разрешения запрещены объединение PR, включение auto-merge, обход `Protect main`, прямые записи в `main`, force push/переписывание истории `main` и удаление незавершённых веток. Если ветки или PR технически недоступны, сообщи об этом, **не обходи правило прямой записью в `main`**. Несвязанные задачи по возможности оформляй отдельными PR.

## 7. Данные и итоговый отчёт

Коммерческие предложения, опубликованные реквизиты и контакты проекта считаются публичными по указанию владельца. Не публикуй пароли, токены и секретные ключи; не удаляй пользовательские данные без соответствующего задания.

Завершая задачу, кратко укажи: **статус, причину, изменения/файлы, фактические проверки, ссылку на PR и оставшиеся проблемы**. Аудит не называй исправлением. Готовность означает проверенное изменение в рабочей ветке и подготовленный PR; **объединение с `main` — отдельное действие только после одобрения владельца**.
